# Marina Custom Apps v0.53.3 — POS Reconciliation Single Architecture

## Release contents

- POS Reconciliation Run is now a **Single** control DocType. Each execution has a separate POS Reconciliation Execution audit record.
- POS Reconciliation Record is canonical by source transaction, not by numbered Run; overlapping date windows reuse the same record ID.
- POS Reconciliation Period Lock manages financial-period closing and reopening separately from the Single control.
- Marina Bank Statement Transaction has a read-only POS Profile (when one unambiguous profile is known) and a linked child table of settled POS Reconciliation Records. The child status labels are Fully Matched and Bank Only - Settled.
- Existing Finance review and accounting posting safeguards remain. GL Entries and existing accounting entries are not regenerated by the migration.
- No destructive historical-data reset or deletion utility is included in this production release.

## Pre-migration requirements for Live

1. **Do not deploy until a complete restorable Live database and files backup has been independently verified.** A failed backup summary is not proof that a usable backup exists.
2. Confirm that no POS Reconciliation Record, POS Accounting Posting (including drafts or children), POS Bank Settlement or associated child transaction rows exist, and no Bank POS Transaction has linked Journal Entries or accounting postings. Confirm no Marina Bank Statement Transaction is linked to an old POS Run, and no job is Queued/Running. The pre-model-sync patch refuses migration if these preconditions are violated.
3. The imported Bank POS Transactions and imported Marina Bank Statement Transactions are **not deleted** by this release. No source imports should be reimported or manually deleted as part of this migration.
4. Confirm existing ERPNext app migrations are up to date and take note of the current Live commit and Frappe/ERPNext versions.

## Deployment

- Merge this release into GitHub `main` separately from any operational deployment.
- Schedule a deployment window. Back up and validate Live data first.
- Deploy the approved `main` revision and run the normal Frappe Cloud migration, or `bench --site marina.frappe.cloud migrate` if the platform does not run it automatically.
- Clear cache only if needed. Verify `frappe.get_meta("POS Reconciliation Run").issingle == 1` and that the new execution and period-lock doctypes are present.
- Open the Single control, choose dates and **Bank Account** explicitly for bank-statement matching. An empty Bank Account skips bank-statement reconciliation.
- On a small date range, verify POS statement matching, settled statuses, execution logs, bank transaction links, the POS Profile and contributing POS record child table.
- Repeat with overlapping ranges and confirm POS Reconciliation Record IDs stay stable and no duplicate posting/allocations are created.
- Verify the unchanged audit/Finance review, bank statement and accounting workflows.

## Operational notes

- The new child table on Marina Bank Statement Transaction is populated on execution; deploying the schema alone does not backfill previously reconciled rows.
- A Bank Statement settlement may contain POS Reconciliation Records from multiple profiles. The statement's main POS Profile is blank in that case and each child row indicates its profile.
- An incomplete or failing migration **must halt deployment**; never bypass its safeguards by dropping or force-deleting financial records.
- The old numbered Run table is not dropped by the migration, but reverting DocType metadata after operations would not be a safe rollback. Restore the verified backup and the previous application revision together if the initial migration must be reversed. After new transactions/postings, design a specific rollback.
